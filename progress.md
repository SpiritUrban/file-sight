# FileSight — прогрес

Останнє оновлення: 2026-07-21 (після реальної перевірки ітерації 2).

## Поточний стан

Ітерації 1 і 2 завершені та перевірені вручну на Windows. Повний цикл
працює: `scan` → `validate` → `rename --dry-run` → `rename --apply` →
`undo --apply`. Файли перейменовуються безпечно (двофазний алгоритм,
журнал, відкат), сторонні файли не перезаписуються, вміст файлів не
змінюється (перевірено SHA-256).

## Виконано (ітерація 2)

- [x] Команда `validate` (REPORT, `--strict`): структура, заборонені
      символи, зарезервовані назви Windows, path traversal, зміна
      розширення, дублікати, зайняті цілі, відсутні/змінені файли.
- [x] Команда `rename` (REPORT, `--dry-run`, `--apply`, `--yes`,
      `--log`, `--limit`, `--resolve-conflicts`); dry-run за замовчуванням,
      підтвердження при `--apply`.
- [x] Команда `undo` (LOG, `--dry-run`, `--apply`, `--yes`); повторний
      undo — безпечний no-op.
- [x] Двофазне перейменування (обмін назвами, цикли, зміна лише регістру).
- [x] Журнал `filesight-rename-log-*.json`: створюється до змін,
      атомарно оновлюється під час операції (tmp + fsync + replace).
- [x] Контрольований відкат при помилці й Ctrl+C; частковий стан чесно
      фіксується (`partially_rolled_back` / `partially_undone`).
- [x] `scan` тепер пише `source_metadata` (size + mtime_ns),
      `rename_enabled: true` і абсолютні шляхи; schema_version 1.1,
      звіти 1.0 читаються з попередженням.
- [x] Пропуски: failed-записи, `rename_enabled: false`, незмінна назва,
      понад `--limit`.
- [x] Стабільні exit codes (0/1/2/3/4/5/6/130), задокументовані в README.
- [x] 75 pytest-тестів (22 з ітерації 1 + 53 нових), без нейромережі.
- [x] README, docs/iteration-02.md оновлені за фактичною поведінкою.

## Команди, що працюють

```powershell
filesight scan PATH [--recursive --output --max-files --language --overwrite-report]
filesight validate REPORT [--strict]
filesight rename REPORT [--dry-run|--apply] [--yes --log --limit --resolve-conflicts]
filesight undo LOG [--dry-run|--apply] [--yes]
python -m filesight <усі ті самі команди>
```

## Результат тестів

75 passed (робочий venv і чистий venv за README). Тести не завантажують
модель; помилки ОС інжектуються через monkeypatch `os.rename`.

## Результати ручної перевірки (2026-07-21, Windows 11)

У тимчасовій папці з реальними зображеннями:

- `scan` → `validate` (valid) → `rename` dry-run (файли не змінені) →
  `--apply --yes` (2 перейменовано, журнал створено) → `undo --apply`
  (назви відновлено) → повторний undo ("already undone", без змін).
- SHA-256 всіх 4 файлів до/після повного циклу — ідентичні.
- Failed-запис (`broken.png`) пропущено; `rename_enabled: false` пропущено.
- Обмін назвами `a.jpg ↔ b.jpg` виконано і скасовано коректно.
- Зміна лише регістру `photo.jpg → Photo.jpg` працює (і undo теж).
- Конфлікт зі стороннім файлом блокує операцію (exit 3, файл недоторканий).
- `--resolve-conflicts` дав `taken-002.jpg`; фактична назва — у журналі.
- `--apply` без `--yes` у неінтерактивному режимі не виконує змін.
- Старий звіт 1.0 (без метаданих): попередження + працює; `--strict` → exit 3.

## Проблеми Windows, виявлені та враховані

- PowerShell/Notepad зберігають JSON з UTF-8 BOM — читання звітів і
  журналів переведено на `utf-8-sig` (виявлено реальним тестом).
- `sys.stdin.isatty()` на null-девайсі Windows може повертати True —
  відмова від підтвердження обробляється додатково через typer.Abort.
- Зміна лише регістру потребує проміжного імені — вирішено двофазним
  алгоритмом для всіх операцій.
- Довгі шляхи: venv не встановлюється у глибоко вкладені папки
  (WinError 206) — це обмеження Windows, не FileSight; для цільових
  шляхів > 259 символів валідація дає PATH_TOO_LONG.

## Відомі ризики

- Перевірка "той самий файл" — розмір + mtime (без хешу): навмисну
  підміну з тими самими метаданими не буде виявлено.
- Другий Ctrl+C під час відкату може залишити файли з назвами
  `.filesight-tmp-*` (розташування зафіксоване в журналі, дані цілі).
- Журнал вважається довіреним; його ручне редагування не валідується
  так суворо, як звіт.
