# FileSight — ітерація 2

## Мета

Безпечне перейменування файлів на основі JSON-звіту з ітерації 1:
перевірка звіту, dry-run за замовчуванням, журнал операції, контрольований
відкат при помилці та повноцінне скасування (undo).

## Фактично реалізовано

- Нові команди CLI: `validate`, `rename`, `undo`. Жодна з них не імпортує
  PyTorch і не завантажує модель — запускаються миттєво.
- `scan` розширено: тепер зберігає `source_metadata` (розмір + mtime у
  наносекундах) та `rename_enabled: true` для кожного успішного запису;
  шляхи тепер завжди абсолютні. `schema_version` піднято до `1.1`,
  звіти `1.0` підтримуються (з попередженням про відсутні метадані).
- Валідація звіту: структура, заборонені символи Windows, зарезервовані
  назви (CON, PRN, AUX, NUL, COM1–9, LPT1–9), назви з крапкою/пробілом у
  кінці, path traversal і будь-які шляхи в `suggested_name`, зміна
  розширення, довжина повного шляху (>259 симв.), відсутні/змінені вихідні
  файли, дублікати джерел і цілей, цілі, зайняті сторонніми файлами.
- Редагування звіту користувачем — нормальний сценарій: `suggested_name`
  можна міняти вручну, `rename_enabled: false` вимикає окремий файл,
  файли з BOM (Notepad/PowerShell) читаються коректно.
- `rename` без прапорців = dry-run; реальні зміни лише з `--apply`;
  інтерактивне підтвердження або `--yes`; `--limit N` (стабільний порядок
  звіту); `--resolve-conflicts` (авто-нумерація `-002`, `-003`, змінює лише
  план і журнал, не звіт); `--log PATH`.
- Undo: dry-run за замовчуванням, `--apply --yes`, перевірка що файл той
  самий (розмір), повторний undo — безпечний no-op.

## Двофазний алгоритм перейменування

1. **Фаза 1**: кожен файл → унікальна тимчасова назва
   `.filesight-tmp-<uuid><ext>` у тій самій папці.
2. **Фаза 2**: тимчасові файли → фінальні назви.

Це коректно обробляє обмін назвами (`a↔b`), цикли з N файлів і зміну лише
регістру на Windows. Використовується тільки `os.rename` — він падає, якщо
ціль зайнята, тому сторонній файл фізично неможливо перезаписати
(`os.replace` на зайняту ціль не використовується ніде).

**Відкат при помилці** — тим самим двофазним способом у зворотний бік:
спочатку всі файли з фінальних позицій повертаються у тимчасові (це
розриває можливі цикли), потім тимчасові → початкові назви. Файли, які не
вдалося повернути, чесно фіксуються в журналі зі своїм фактичним
розташуванням (`status: failed`, `error` з поточним шляхом).

Ctrl+C під час операції обробляється як помилка: зупинка, відкат,
оновлення журналу, exit code 130.

## Формат журналу

`filesight-rename-log-YYYYMMDD-HHMMSS.json` поруч зі звітом (або `--log`).
Журнал створюється **до** першої зміни і атомарно оновлюється після кожного
кроку (запис у `.tmp` → flush+fsync → `os.replace`).

```json
{
  "schema_version": "1.0",
  "operation_id": "uuid",
  "created_at": "2026-07-21T00:41:49Z",
  "completed_at": "2026-07-21T00:41:50Z",
  "report_path": "...\\filesight-report.json",
  "status": "completed",
  "error": null,
  "undone_at": null,
  "summary": { "planned": 2, "completed": 2, "failed": 0, "rolled_back": 0, "undone": 0 },
  "operations": [
    {
      "original_path": "...\\IMG_0001.JPG",
      "final_path": "...\\blue-background-with-abstract-design.JPG",
      "temporary_path": "...\\.filesight-tmp-<uuid>.JPG",
      "size_bytes": 1602752,
      "status": "completed",
      "error": null
    }
  ]
}
```

Статуси операцій/журналу: `planned`, `in_progress`, `completed`, `failed`,
`rolled_back`, `partially_rolled_back`, `undone`, `partially_undone`.
`size_bytes` записується під час rename і використовується undo для
перевірки, що файл не був підмінений.

## Алгоритм undo

Для кожної операції зі статусом `completed`: `final_path → original_path`,
тим самим двофазним виконавцем (тому undo обміну/циклів/регістру працює).
Перед виконанням перевіряється: журнал валідний, є що скасовувати, фінальні
файли існують, розмір збігається із записаним, початкові шляхи вільні (або
зайняті іншими файлами цього ж undo-плану). Після успіху журнал отримує
`status: undone` і `undone_at`; повторний `undo --apply` завершується
повідомленням без змін. Якщо undo зазнало помилки і всі файли повернуто в
перейменований стан — статус журналу залишається `completed` (undo можна
повторити); якщо якийсь файл застряг — `partially_undone` з деталями.

## Правила конфліктів

- Ціль, зайнята файлом поза планом → блокування всієї операції
  (`TARGET_ALREADY_EXISTS`, exit 3).
- Дві цілі з однаковою назвою (без урахування регістру) → `DUPLICATE_TARGET`.
- `--resolve-conflicts` замість блокування додає `-002`, `-003`, ...
  (стабільно, у порядку звіту), показує результат у dry-run і записує
  фактичні назви в журнал; вихідний JSON-звіт не змінюється.
- Ціль, що збігається з джерелом іншого запису плану — дозволена
  (файл звільнить місце у фазі 1); це і робить можливими обміни й цикли.

## Гарантії безпеки

- Без `--apply` жоден файл не змінюється.
- Сторонні файли ніколи не перезаписуються (тільки `os.rename` на вільну ціль).
- Перейменування відбувається лише в межах папки файла; `suggested_name` —
  лише ім'я, не шлях.
- Розширення незмінне (регістр розширення завжди береться з оригіналу).
- Журнал існує до першої зміни; частковий стан ніколи не приховується.
- Вміст файлів не читається і не пишеться — лише rename; хеші збігаються
  до/після (перевірено вручну SHA-256).

## Відомі обмеження

- Метадані — розмір + mtime, не криптографічний хеш: підміну файла з тим
  самим розміром і mtime виявлено не буде.
- Другий Ctrl+C під час відкату може залишити файли в тимчасових назвах
  (вони зафіксовані в журналі; назви починаються з `.filesight-tmp-`).
- `undo` після ручного редагування журналу не захищений від усіх помилок
  користувача (журнал вважається довіреним).
- Відносні шляхи у старих звітах ітерації 1 резолвляться відносно поточної
  робочої папки; нові звіти завжди містять абсолютні шляхи.
- Ліміт довжини шляху — класичний MAX_PATH (259); довгі шляхи з
  `\\?\`-префіксом не підтримуються.

## Ручний сценарій перевірки

1. `filesight scan <папка>` → звіт.
2. `filesight validate <звіт>` → "Report is valid".
3. Відредагувати `suggested_name` одного запису; поставити
   `rename_enabled: false` іншому.
4. `filesight rename <звіт>` → план; файли не змінені.
5. `filesight rename <звіт> --apply --yes` → нові назви + журнал.
6. Створити сторонній файл з назвою цілі; повторити rename → блокування.
7. `--resolve-conflicts` → назва з `-002`.
8. `filesight undo <журнал> --apply --yes` → початкові назви.
9. Повторний undo → "already undone".
10. SHA-256 всіх файлів до/після — ідентичні.
